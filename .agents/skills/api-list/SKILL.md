# API List

以使用者的語言列出專案實際提供的 API。預設掃描目前工作目錄；使用者指定服務或子目錄時依指定範圍處理。

## 探索

- 讀取適用的專案指引，辨識框架、入口、路由註冊與 OpenAPI/Swagger 規格。使用 `rg --files` 和針對框架的 `rg` 搜尋，排除依賴與建置產物。
- 追蹤 router 掛載前綴、版本、HTTP 方法與動態參數，組成完整路徑。對檔案式路由、Edge Functions、GraphQL 和 RPC，依實際結構表達，不把一般函式當作 HTTP API。
- 優先以實作確認行為。規格與實作不一致時標記差異；只有規格可用時註明未經實作確認。
- 預設列出專案提供的端點；只有使用者要求時才列出呼叫的外部 API。
- 不讀取或輸出 `.env`、憑證與 token。以環境變數組成的網址用變數名稱表示。以靜態讀取盤點，不為探索呼叫會修改資料的端點。

## 輸出

預設使用三欄表格：「API 名稱」、「用途」與「Worker 中的名稱」。讀者是不會寫程式的人，使用日常語言說明功能，例如「取得行程清單：查看所有已建立的行程」及「新增行程：將新的行程儲存到行事曆」。

「Worker 中的名稱」填寫實際處理該功能的函式名稱，例如 `readEvents` 或 `createEvent`，方便對照 Worker。若沒有具名函式，標示「未命名」；專案沒有 Worker 時標示「不適用」，不可猜測名稱。

API 名稱優先使用現有的易懂功能名稱；若只有程式名稱，依已確認的行為改寫為白話名稱。同一路徑提供不同功能時分列，例如取得行程與新增行程。不把 CORS 預檢等技術輔助操作列入一般功能清單。

用途只描述使用者能完成的事情，不列出 HTTP 方法、網址路徑、參數、JSON、驗證設定、程式碼位置或其他實作細節。只有使用者另外要求技術資訊時才補充。

只列出實作或規格支持的功能，不猜測。功能很多時依用途分組；若僅列出部分，簡短說明省略範圍，不宣稱完整。

若找不到 API，說明已檢查的入口和範圍，以及可能缺少的後端或規格。除非使用者要求，直接在對話回覆，不修改程式或另建報表。
